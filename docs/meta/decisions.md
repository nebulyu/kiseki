## D-001：本地优先

日记和决策信息高度敏感。SQLite 数据库默认位于本地，API Key 不进入数据库。是否发送原文给外部模型由配置明确决定。

## D-002：CLI 优先

当前最大风险是评分是否稳定、可解释，而不是界面是否精美。CLI 足以验证完整数据链路，并降低早期改动成本。

该决定记录起步阶段的选择。CLI 闭环现已完成；后续是否增加 UI 以实际使用负担判断，不再要求等评分校准或路线系统全部完成，见 D-015。

## D-003：原文与分析分离

这项设计对于长期系统合理，但对当前个人原型过早。第一版将原文和当前分析保存在同一条 `daily_records` 中；只有确实需要比较多次分析时才拆表。

## D-004：结构化输出

自由文本回复无法可靠入库和比较。模型响应必须经过 Schema 约束与运行时校验，校验失败即记为失败分析。

## D-007：未知不等于中性

原文未提及某个维度，只能说明信息不足。使用 null 可以避免大量虚假的 50 分污染长期曲线。

## D-009：原型优先

第一版的目标是尽快得到能被本人每天使用的工具。起步只实现 `add`、`list` 和 `show`，直接调用一个模型 API，采用一张 SQLite 表，不设置测试覆盖率、自动重试、迁移框架和通用 Provider 接口。进入真实校准阶段后新增的 `review` 仍遵守这些简化边界。

## D-010：人工校准不覆盖 AI 原始结果

人工 Review 是评分校准证据，不是对模型 JSON 的原地编辑。`accepted`、`adjusted`、`rejected` 独立保存在同一记录的 `review_json` 中；最终有效分数由当前 AI 分析与仍匹配该分析版本的 Review 在读取时合成。分析版本变化后保留旧 Review，并派生为 `stale`。

## D-011：路线开发与日常使用并行

持续使用和 Review 用于验证评分，路线 MVP 用于验证长期观察是否有价值。两者可以并行；先前路线图中“评分验证后才开发路线”的顺序不再作为限制。校准汇总仍可后续开发。

## D-012：不混合不同分数的含义

目标表达期望状态，路线表达实现方式。每日体验分、路线当日影响、阶段成果和持续消耗分别展示。旧路线样例中的初始 50 分、六维加权和窗口衰减方案不作为本次 MVP 的计算依据；新样例使用可解释的信号规则，缺少证据保持 null。

## D-013：路线结果与每日结果独立

路线分析可以直接使用原文，不要求已有每日分析或人工确认。每日 Review 不自动认可路线结果；路线 Review 也不能改写日记和每日评分。第一次路线接入采用显式、单篇、单路线的调用，暂不和 `add` 自动联动。

## D-014：路线存储与模块扩展待实现

拟议使用同一 SQLite 中独立的 `route_analyses` 保存当前路线结果、配置快照和独立 Review。现有单表约束仅服务于日记原型，不限制有实际一对多关系的路线扩展。具体契约见 [长期目标与路线 MVP](../long-term-routes.md)，本轮只修改文档与配置样例，不创建模块、表或新依赖。

## D-015：UI 时机取决于实际使用

当 CLI 操作妨碍持续记录或人工确认时，可以提前引入本地界面。当前没有开始 UI 实现，也未确定 React、Tauri 或其他技术；保持交互与业务函数分离即可，不提前安装框架。
