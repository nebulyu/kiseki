## D-001：本地优先

日记和决策信息高度敏感。SQLite 数据库默认位于本地，API Key 不进入数据库。是否发送原文给外部模型由配置明确决定。

## D-002：CLI 优先

当前最大风险是评分是否稳定、可解释，而不是界面是否精美。CLI 足以验证完整数据链路，并降低早期改动成本。

## D-003：原文与分析分离

这项设计对于长期系统合理，但对当前个人原型过早。第一版将原文和当前分析保存在同一条 `daily_records` 中；只有确实需要比较多次分析时才拆表。

## D-004：结构化输出

自由文本回复无法可靠入库和比较。模型响应必须经过 Schema 约束与运行时校验，校验失败即记为失败分析。

## D-007：未知不等于中性

原文未提及某个维度，只能说明信息不足。使用 null 可以避免大量虚假的 50 分污染长期曲线。

## D-009：原型优先

第一版的目标是尽快得到能被本人每天使用的工具。起步只实现 `add`、`list` 和 `show`，直接调用一个模型 API，采用一张 SQLite 表，不设置测试覆盖率、自动重试、迁移框架和通用 Provider 接口。进入真实校准阶段后新增的 `review` 仍遵守这些简化边界。

## D-010：人工校准不覆盖 AI 原始结果

人工 Review 是评分校准证据，不是对模型 JSON 的原地编辑。`accepted`、`adjusted`、`rejected` 独立保存在同一记录的 `review_json` 中；最终有效分数由当前 AI 分析与仍匹配该分析版本的 Review 在读取时合成。分析版本变化后保留旧 Review，并派生为 `stale`。
