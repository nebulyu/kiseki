# 长期目标与路线 MVP 规格

状态：配置加载与查看已实现；路线分析、独立存储、Review 和时间线尚未实现。最后更新：2026-09-07。

本文是目标与路线功能的实现依据。当前在原有日记命令之外，已支持 `route list` 和 `route show <route_id>`，仅用于查看配置。下文明确标为计划的分析、计算、独立 Review 和新增存储尚未接入。

## 目标与开发顺序

长期目标系统帮助用户观察：希望达到什么状态、采取哪条路线、已有记录提供了哪些进展或阻碍证据、是否值得调整投入。日常记录和每日评分校准持续进行；路线 MVP 可以同时开发，不以积累固定数量的 Review 为前置条件。

完整路线 MVP 计划形成以下闭环；本轮只完成第一步的定义加载与查看：

```text
定义目标与路线 -> 选择已有日记 -> 分析相关证据
             -> 计算候选当日影响 -> 独立人工确认 -> 查看路线时间线
```

## 概念与边界

| 概念 | 含义 | 第一版处理方式 |
| --- | --- | --- |
| 目标 Goal | 希望达到或维持的状态，以及个人理由和判断标准 | 配置中定义，不自动判定实现 |
| 路线 Route | 为目标采取的一种方式；一个目标可以有多条路线 | 每条路线关联一个目标 |
| 证据 Evidence | 日记中支持路线判断的片段 | 保存出处，区分计划、尝试、完成、受阻和其他观察 |
| 当日影响 Route Delta | 某条记录中的证据按路线规则映射出的候选影响 | `-5` 到 `5` 的整数或 `null`，不等于长期完成度 |
| 里程碑 Milestone | 可以由用户确认的阶段成果 | 先写在目标判断标准中，后续再实现状态管理 |
| 积累 Asset | 可以继续使用的成果、经验或资源 | 第一版只保留相关证据，不建设资产库 |
| 成本 Cost | 精力、时间等消耗的记录 | 保留成本证据，不用总分隐藏成本 |

整体体验分、六维评分、路线当日影响和长期状态分别表达不同问题。第一版不使用“初始 50 分 + 每日增量”生成长期总分，不给出成功概率，也不自动排名路线。目标允许没有截止日期；维持状态或探索方向也可以写成自由文本标准。

## 本地配置

样例与个人数据分开：

| 位置 | 用途 |
| --- | --- |
| `docs/templates/goal-definition.example.yaml` | 虚构目标样例，顶层包含 `goals` 列表，可作为个人目标文件的起点 |
| `docs/templates/route-definition.example.yaml` | 虚构路线样例，一个文件定义一条路线 |
| `private/goals.yaml` | 由用户维护的目标文件，当前默认加载路径 |
| `private/routes/*.yaml` | 由用户维护的路线文件，当前默认加载范围 |

默认路径相对于项目位置解析，不依赖执行命令时的工作目录。公开模板只展示格式，不会被作为默认个人配置；创建个人文件的 PowerShell 步骤见 [README](../README.md#配置并查看长期目标与路线)。真实目标与路线属于私人信息，存放在已经被 Git 忽略的 `private/`；程序不会自动生成或覆盖它们。

目标包含 `id`、`version`、`name`、`status`、`description`、`motivation`、`target_date`、`success_criteria` 和 `constraints`。目标状态为 `active`、`paused` 或 `completed`，由用户维护。`target_date` 可以为空；非空日期使用带引号的 `YYYY-MM-DD` 字符串。

路线包含 `id`、`version`、`goal_id`、`name`、`status`、`description`、`key_hypotheses`、`focus_dimensions`、`specific_signals`、`costs` 和 `calculation`。路线状态为 `exploring`、`active`、`paused` 或 `archived`。所有状态均可查看，包括暂停、完成目标和归档路线；后续路线分析才限制为 `exploring`/`active` 路线，且关联目标必须为 `active`。

加载使用 `yaml.safe_load` 和 Pydantic，检查必需字段、基本类型、状态枚举、合法日期和版本；不接受未知字段，不将字符串分值或布尔值转换成整数。目标 ID 在目标文件中唯一，路线 ID 跨路线文件唯一，`goal_id` 必须存在。损坏 YAML、未知版本和无效引用会说明文件与具体问题并失败退出，不静默跳过、不自动迁移。

`focus_dimensions` 只能使用 `technical_growth`、`relationship_capital`、`information_gain`、`social_engagement`、`wellbeing`、`autonomy`，是关注方向，不参与六维分数加权。信号 ID 在同一路线的 `specific_signals` 和 `costs` 中合并检查唯一性；正向 `daily_delta` 为 `1..5` 整数，成本为 `-5..-1` 整数。

目标文件缺失会给出配置指引并失败退出；目标有效但路线目录不存在或没有 `.yaml` 文件时，正常提示尚无路线，不自动创建目录或目标。未知路线 ID 同样失败退出。列表按路线 ID 稳定排序，展示路线 ID、名称、所属目标及双方状态；详情展示两者的定义和内容版本，不输出分析、进度、时间线或默认零分。

`schema_version` 描述配置结构，当前仅支持目标文件 `"0.1.0"` 和路线文件 `"0.2.0"`；`version` 描述某个目标或路线的内容版本，必须为正整数；`formula_version` 描述计算规则。修改目标含义、匹配条件或信号分值时增加对应内容版本。结构不兼容时直接报错，不自动迁移，也不升级每日分析 Schema。

当前 `calculation` 四个字段均必需且只接受以下值，用于校验和展示；本轮不执行实际评分计算：

```yaml
calculation:
  formula_version: "route-evidence-0.1.0"
  method: "sum_unique_signals_clamped"
  daily_delta_range: [-5, 5]
  missing_value: null
```

## 证据识别与候选影响（计划）

第一版一次只分析“一篇日记 + 一条明确选择的路线”。输入使用数据库中的日期和原文，以及该路线和关联目标的完整定义；不要求先完成每日 AI 分析或每日 Review。暂不读取六维结果作为计算输入，因此每日 `analyze` 不会使路线结果自动过期。

模型返回路线关联判断、摘要、证据和置信度，不负责输出最终计算分值。每条证据至少包含：本次结果内唯一的 `id`、`source_excerpt`、`observation_kind`、可为空的 `signal_id` 和 `reason`。`observation_kind` 可为 `planned`、`attempted`、`completed`、`blocked` 或 `observation`；只根据原文区分，不将计划当作成果。

`relevance` 可为 `related`、`no_evidence` 或 `uncertain`。模型只能引用当前配置中的信号 ID，并解释为何满足 `match_when`。校验至少应确认原文片段能在本次日记中找到、信号 ID 存在，且 `no_evidence`/`uncertain` 结果不带已匹配信号；格式错误作为分析失败处理，不增加 JSON 修复流程。

本地使用以下固定规则，不建设规则引擎：

1. `relevance` 为 `related` 且至少匹配一个已定义信号时，对去重后的信号 ID 求和：`candidate_delta = clamp(sum(daily_delta), -5, 5)`。
2. 同一信号在同一篇日记里只计一次；多段引用仍保留供查看。推动信号使用 `1` 到 `5`，成本信号使用 `-5` 到 `-1`。
3. 没有相关证据、无法判断，或有相关证据但未匹配任何已定义信号时，`candidate_delta` 为 `null`，并显示原因。
4. 已匹配的正负信号相抵时可以得到 `0`；`null` 不参与求和，也不转换为 `0` 或负分。
5. 置信度反映证据支持程度，不作为分数乘数。推动与成本证据分别可见，即使净影响为零。

信号分值是用户可调整的候选规则，不是普适标准。一次成果可对多条路线有意义，但第一版不计算跨路线贡献总量。同一成果被多篇日记提及时，时间线保留这些观察，不把它们相加宣称为多份成果；跨记录成果识别与去重留给后续里程碑/资产功能。

## CLI 与交互

以下命令均以 `uv run python app.py` 开头，仅前两条已实现：

| 命令 | 状态与行为 |
| --- | --- |
| `route list` | 已实现：本地列出所有路线、关联目标与状态 |
| `route show <route_id>` | 已实现：显示目标背景、成功标准、约束及路线规则和内容版本；尚无分析时间线 |
| `route show <route_id> --record <record_id>` | 计划：查看某条日记的路线证据、候选结果与人工确认 |
| `route analyze <record_id> <route_id>` | 计划：显式调用一次模型，只处理指定日记和路线 |
| `route review <record_id> <route_id>` | 计划：本地确认指定路线分析，不调用模型 |

已实现的两条命令完全本地，只读取目标与路线配置，不读取 `.env`、不调用模型，也不读取、初始化或修改日记数据库。其他命令和帮助信息不提前加载路线配置。

第一版不增加自动分析全部路线、与 `add` 自动联动、批量重算或配置编辑向导。已有成功路线分析时，重算前默认 No 确认；成功后替换当前候选结果，失败时保留旧结果。请求提示模型、耗时和失败信息，复用现有模型连接配置、超时设置和无自动重试策略。

## 独立路线 Review（计划）

每日 Review 不能代表用户认可路线判断。路线 Review 绑定具体的路线分析 revision，保存自己的状态、可选分值覆盖、原因和时间：

- `accepted`：认可候选结果，沿用候选 delta。
- `adjusted`：显式覆盖为 `-5` 到 `5` 的整数或 `null`，要求一句修正原因；无覆盖与显式 `null` 必须区分。
- `rejected`：否决本次路线分析，要求原因，有效 delta 不可用。
- `unreviewed`：没有人工确认，显示候选值并明确标记，不宣称已经确认进展。
- `stale`：已有 Review 对应旧分析 revision，旧覆盖不套用到新分析；新候选值仅供参考。

已有 Review 被替换前需要确认；Skip 不保存。第一版只调整当日影响和原因，不直接改写模型证据；误提取的事件可否决并说明。接受路线分析也不会自动完成目标、里程碑或新增资产。

## 存储与版本边界（计划）

现有 `daily_records` 不因路线功能改变日记或每日评分语义。计划新增 `route_analyses`，以 `(record_id, route_id)` 唯一标识一篇日记对一条路线的当前分析；结果与每日 `analysis_json`、每日 `review_json` 独立保存。

最少保存：日记/路线 ID、成功分析所用的目标与路线配置快照、模型与路线提示词版本、公式版本、分析 revision、结构化证据与候选 delta、独立 Review JSON、最近错误和成功分析时间。新分析尚未成功时，成功结果字段可以为空；重分析成功后 revision 增加，旧 Review 保留并派生为 stale。失败只更新最近错误，不改动旧成功结果、快照、revision 或 Review。

配置版本或规范化后的配置内容与成功结果快照不一致时，分析显示 `outdated`。它表示分析口径变化，与 Review 的 `stale` 分开显示；即使用户忘记增加配置 version，也不能把旧结果标成当前规则下的结果。旧结果及 Review 可以查看，但不作为当前配置下的有效结果，也不能通过再次接受旧结果消除 outdated，需要明确重分析。

同一日记与路线重算不新增贡献记录，不复制日记。时间线按快照展示旧规则，不用当前配置重新解释旧分数；配置文件被移除后，已经保存的结果仍可通过快照查看。第一版没有分析历史表，只保留最新成功结果及与之可能不匹配的上一次 Review；重分析会替换上一次成功结果，这一点应在确认提示中说明。

## 当前代码边界与后续扩展

本轮已实现以下配置模块；继续使用普通函数，不增加服务容器或预留空模块：

```text
app.py          注册 route 子命令，保留现有命令
route_cli.py    配置列表、详情和错误呈现
routes.py       YAML 加载、配置校验与目标关联
```

加载函数允许传入配置路径，返回结构化对象，不依赖 `input()` 或 `print()`，便于临时样例检查和未来 UI 复用。PyYAML 由 uv 添加到项目依赖并锁定。只有执行路线命令时才加载个人配置；现有 `model.py`、`database.py`、每日 Schema 和 Review 逻辑不因本轮功能改变。

下一阶段按需要增加路线模型结果、候选影响计算和独立存储，再接入独立 Review 与时间线，不预先建设规则引擎。

## 隐私与后续范围

拟议的 `route analyze` 会向当前模型服务发送指定日记原文、日期、所选路线及关联目标定义，包括其中的个人理由和限制。用户应在命令帮助与确认流程中了解此范围；不发送其他日记或其他路线。查看、加载配置和路线 Review 仅在本地完成。

后续再考虑：里程碑状态、资产库、周月复盘、配置版本间重算、机会窗口、路线比较和 UI。不同目标的分数不能直接排名，记录中的关联不能自动推断为因果，任何路线结果都不自动替用户做出人生选择。

## 分步交付与完成判断

1. 已实现配置加载：目标/路线定义可加载，`route list/show` 能解释关联和规则；没有路线时明确显示空状态，缺少目标或配置错误时失败退出。
2. 下一阶段路线分析：单篇日记对应单条路线、简单信号计算、独立保存、失败保留旧结果、原地重算可用。
3. 后续确认与时间线：独立 Review、版本差异显示、按日期回看证据构成最小闭环。

当前配置功能使用项目 uv 环境、临时目录和虚构 YAML 做轻量自检，不调用真实模型或改动私人配置、日记与数据库。后续分析功能再用少量合成记录检查：计划不会匹配完成信号、无相关证据保持 null、重复信号不重复计分、失败不破坏旧结果、重分析不增加记录且使旧 Review stale、配置变更显示 outdated、原有日记命令保持兼容。真实调用由用户明确选择一篇日记和一条路线验证，不建立完整测试平台或覆盖率门槛。
