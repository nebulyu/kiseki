# 项目路线图

路线图服务于个人使用，不设置严格工程门槛。每一步都以“是否已经产生真实价值”为判断依据。

从 2026-09-06 起，Phase 2 的日常使用与 Phase 3 的路线 MVP 开发并行推进。阶段编号表达功能层次，不要求评分校准全部完成后才能开发路线。路线功能的具体范围以 [长期目标与路线 MVP 规格](long-term-routes.md) 为准。

## Phase 0：定义与准备

状态：已完成

- 明确项目目标和评分维度。
- 准备输入、输出和提示词模板。
- 安装 uv。
- 初始化简单 Python 项目。

完成后直接进入实现，不继续扩写架构。

## Phase 1：可用的 CLI 原型

状态：已完成

- `add`：输入感想、调用模型、保存结果。
- `list`：快速查看历史记录。
- `show`：查看原文和完整分析。
- SQLite 使用一张 `daily_records` 表。
- 模型调用直接写成一个清楚的函数。

当它能够保存并展示几条真实日记时，就开始使用，而不是继续补充测试和通用能力。

## Phase 2：个人试用与评分调整

状态：进行中

- 连续使用一到两周。
- 使用 `review <id>` 接受、修正或否决候选分析，并保留校准原因。
- 使用 `analyze <id>` 原地恢复失败分析或经确认重新分析，观察同步等待和 120 秒超时是否适合日常使用。
- 记录哪些分数符合直觉，哪些解释明显不对。
- 直接调整提示词、维度定义和输出格式。
- 观察自己是否愿意每天打开它。

这个阶段的核心产物是个人反馈，不是测试覆盖率或评估平台。

## Phase 3：长期路线

状态：进行中；2026-09-07 完成目标/路线配置加载与查看。

近期按三个小步骤实现：

1. 已完成：目标/路线 YAML 加载与校验、`route list` 和 `route show <route_id>`；所有配置状态可见，完全本地，不访问日记数据库或模型。
2. 下一阶段：单篇日记对应单条路线的证据识别、候选当日影响和独立存储。
3. 后续：独立路线 Review、配置版本差异与证据时间线。

计划中的路线分析读取原文，不要求日记先通过每日 Review。当前仅展示配置规则，不做信号匹配或分数计算。开发可与真实日记、校准数据积累并行；`calibration` 汇总保留为后续能力，不成为路线开发门槛。

第一版只使用清楚的信号配置和简单计算，不预建规则引擎，不将每日增量累加为长期成功概率。里程碑管理、资产积累、周月复盘、机会窗口和路线比较等到最小闭环实际使用后再加入。

## Phase 4：更方便的界面

状态：待定，尚未选择 UI 技术。

当 CLI 开始妨碍日常使用时，再选择合适的本地界面：

- 输入每日感想。
- 查看评分和解释。
- 浏览历史和趋势曲线。
- 调整路线配置。

界面可以根据实际使用需要提前，不必等路线系统全部完成。继续保持终端交互与业务函数分离，具体技术在开始 UI 实现时决定。

## 暂不考虑

- 多人协作和社交功能。
- 云同步与账号系统。
- 企业级权限和审计。
- 微服务、消息队列和高可用设计。
- 面向公众的统一人生评分标准。
